# Shared Charge: fair access to shared EV chargers

A game theory semester project. A small charging-queue simulator tests whether an **idle penalty** (a fee for leaving a fully charged car in the bay) reduces waiting, and how it affects drivers with different needs. A local results screen shows the experiments, the evolutionary graph and the game calculations.

**Research question:** Does an idle penalty reduce waiting, and how does it affect drivers with different needs?

**Short answer from the experiments:** a fee of 2 points per idle slot cut waiting and raised full service in all 15 matched comparisons (3 demand levels × 5 seeds). It raised drivers' net utility only at medium and high demand, mostly for Urgent drivers. At low demand both driver types ended worse off. Drivers programmed to always hold did not change behaviour; they only paid. See `reports/final_report.pdf`.

## Reproduce everything with one command

```powershell
python -m shared_charge all
```

This (1) generates the five seed folders if they are missing, (2) checks the supplied mini case and stops if it fails, (3) runs the 30 main and 10 control experiments, (4) computes the game-theory and evolutionary results, and (5) draws the figures. It takes about 15 seconds. The results are deterministic: running it again gives identical files (only the timestamp in `results/manifest.json` changes).

Individual steps:

```powershell
python -m shared_charge generate                 # data/generated/data_seed_0..4 (add --force to rebuild)
python -m shared_charge minicase                 # one-charger mini case, exit code 0 if it matches
python -m shared_charge run --demand medium --policy P1 --seed 0            # one run, saved to results/runs/
python -m shared_charge run --demand medium --policy P1 --seed 0 --control  # same, every driver on fixed Hold
python -m shared_charge games                    # results/game_theory.json, results/evolutionary.csv
python -m shared_charge figures                  # results/figures/*.png
```

Seed inputs can also be generated by hand with the supplied script. **Always pass `--output`**, because its default folder is `starter_data/` itself:

```powershell
python starter_data/generate_data.py --output data/generated/data_seed_0 --seed 0 --urgent-prior 0.30
```

## Run the tests

```powershell
python -m pytest
```

There are 71 tests covering queue order and tie-breaks, hold legality and expiry, forced release, unserved waiting cost, Reciprocal memory across days, Fee aware decisions, privacy of rule inputs, utility, determinism, no double occupancy, the mini case, every game-theory calculation, the 40 saved runs, matched inputs, summaries recomputed from visits, and the API.

## Start the results screen

```powershell
python -m shared_charge serve
```

Then open **http://127.0.0.1:8000** in a browser. Stop with `Ctrl+C`. The screen reads only the saved files in `results/`, so run `python -m shared_charge all` first on a fresh copy.

What you can do on the screen:

* Choose **Demand** (Low, Medium, High), **Policy** (P0, P1, or Compare P0 and P1) and **Seed** (0–4).
* **Run experiment** re-runs the selected run(s) for 60 days and confirms that the results match the saved files.
* **Site:** six bays for any of the 60 days, showing real visits (charging, idle holds, early departures) and the queue.
* **Policies:** P0 against P1 for the seed, plus the change and range across all five seeds.
* **Drivers:** Urgent against Flexible, each driver rule, and the fixed-Hold control.
* **Evolution:** F = 0 and F = 2 trajectories with the first-step check.
* **Games:** normal form, δ threshold, Bayesian check, mixed against behavioral.
* **Visits:** filterable visit table and download links for every CSV/JSON file.
* **Checks:** settings, input-file hashes, event order and the mini case.

To work on the frontend with live reload (API on :8000, Vite on :5173):

```powershell
python -m shared_charge serve            # terminal 1
cd frontend; npm install; npm run dev    # terminal 2, then open http://localhost:5173
```

Rebuild the served copy after changes: `cd frontend; npm run build`.

Optional browser check (screenshots at 1440/1280/768/390 px, console errors, screen-versus-file numbers):

```powershell
python -m playwright install chromium    # once
python scripts/ui_check.py               # with the server running; writes results/ui_check/
```

## Results folder

| File | Contents |
|---|---|
| `results/runs/<run_id>/visits.csv` | One row per visit: seed, demand, policy, day, driver, type, rule, arrival, departure, charger, start, finish, release, requested and delivered kWh, waiting, action, idle slots, fee, penalty, gross and net utility, fully served. `NA` marks a missing value (never started or never finished). |
| `results/runs/<run_id>/summary.json` | Overall, by-type, by-rule and by-action summaries |
| `results/runs/<run_id>/settings.json` | Settings and SHA-256 of every input file |
| `results/summary_runs.csv` | One row per run (40 rows) |
| `results/comparison_by_seed.csv`, `comparison_stats.csv` | P1 − P0 per matching seed, then mean, minimum, maximum |
| `results/control_by_seed.csv`, `control_stats.csv` | Fixed-Hold control comparison |
| `results/mini_case_check.json` | Simulated against expected mini-case values |
| `results/game_theory.json` | All written game-theory calculations |
| `results/evolutionary.csv` / `.json` | 31 points for each of F = 0 and F = 2 |
| `results/figures/` | Report figures, including **`evolutionary.png`** (the evolutionary graph) |
| `results/manifest.json` | Run list and input hashes for each seed |

Run IDs look like `medium_P1_seed3`; control runs look like `control_allhold_medium_P1_seed3`.

## Dataset

`starter_data/` is the teacher's synthetic archive and is never modified (checked by a test against `SHA256SUMS.txt`). The experiments use five folders generated from it with seeds 0–4 and an urgent prior of 0.30. Each has 4,320 requests: 720 low, 1,440 medium and 2,160 high, each over 60 days, with 40 drivers. See `docs/data_audit.md`.

## Scope and limits

P0 and P1 only (no history scores, P2/P3), seeds 0–4, no hardware, payments or real data. All values are synthetic teaching points; the results do not predict behaviour at a real campus.
